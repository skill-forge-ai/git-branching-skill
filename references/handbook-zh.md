# Git 工作流手册（非技术人员版）

**本文讲什么：** 两种主流 Git 工作流（GitHub Flow 和 GitFlow）分别是什么、你的项目该用哪一种，以及**你该怎么对 AI agent 描述你的意图**。

**本文不讲什么：** git 命令。你不需要记住任何一条。

**读者：** 不写代码，但需要对项目的代码管理方式做决策或参与协作的人——产品经理、设计师、运营、创业者、技术管理者。你有一个 AI agent（Claude Code、Cursor、Copilot 等）替你执行具体操作。

**读完你能做到三件事：**

1. 说清楚自己的项目在用哪种工作流，以及为什么用它
2. 用自然语言把意图交代给 agent，让它做对
3. 认出三种"要出事"的信号，知道该说什么、更重要的是不该说什么

---

## 一、先建立心智模型

不理解这三件事，后面的话术都会变成背口诀。

### 1.1 分支是什么

**分支是一份平行的项目副本。** 你在分支上做的任何改动，都不影响其他人看到的版本。

类比：一份共享文档，你复制了一份自己改。改好了，再合并回原文档。区别在于 git 能精确合并，而不是整份覆盖。

为什么需要它：三个人同时改一个项目，如果都直接改同一份，互相覆盖是必然的。每人一个分支，各改各的，最后逐个合回去。

### 1.2 为什么不能直接改"主干"

项目里有一个特殊分支，通常叫 `main`（老项目可能叫 `master`）。**它代表"正式版本"。**

直接往 `main` 上改，等于跳过所有检查直接改线上产品。所以规范的项目都会锁住它：**任何改动都必须先在自己的分支上做，再通过一次审核（叫 Pull Request，简称 PR）合并进去。**

> **这是两种工作流唯一的共同底线，也是最重要的一条。** 如果有人说"这个改动很小，我直接推到 main 就行"——这句话在任何工作流下都是错的。

### 1.3 "发布"到底发生了什么

很多人以为代码合并了就等于用户看到了。**不是。** 完整链路是：

```
在分支上改 → 审核通过 → 合并进 main → 部署到服务器 → 用户看到
```

**合并 ≠ 部署。** 两种工作流最大的差别，就在于"合并"和"部署"之间隔了多远：

- **GitHub Flow**：几乎不隔。合并了就准备上线。
- **GitFlow**：隔着一个"冻结期"。合并了先攒着，到发版日一起上。

### 1.4 一个必须知道的概念：功能开关

**功能开关（feature flag）是一个能在线上随时打开或关闭某个功能的配置项。**

代码已经上线了，但功能是关着的，用户看不见。想上线时打开，出问题时关掉——不需要改代码、不需要重新部署，几秒钟的事。

这个概念在 1.1~1.3 里没有对应物，但它是 GitHub Flow 能成立的关键。第二节会解释为什么。

## 二、GitHub Flow

### 2.1 一句话本质

**只有一个主干 `main`，它永远处于"随时可以上线"的状态。所有改动都是从它拉出去、很快再合回来的短命分支。**

### 2.2 长什么样

```
main ──────●──────●──────●──────●──────▶  （永远可上线，随时部署）
            ╲    ╱ ╲    ╱
             分支1   分支2                  （每个活 1~2 天）
```

### 2.3 日常是什么节奏

1. 要做一个功能 → 从 `main` 拉一个分支
2. 做完（通常 1~2 天）→ 提 PR，等审核和自动测试
3. 通过 → 合并进 `main`
4. 合并后很快就部署上线

### 2.4 关键点：没做完的功能怎么办

这是**最容易被误解的地方**。

一个功能要做两周，但分支只能活两天，怎么办？

**答案：拆开做，每一块都合进 main，但用功能开关关着。** 代码在线上，用户看不见。全部做完了，打开开关，功能就出现了。

> **划重点：GitHub Flow 不是"规则更少"，而是"把隔离未完成工作的手段从分支换成了开关"。**
>
> 只采纳"规则更少"、不采纳功能开关的团队，会得到一堆活了好几周的长命分支——既没有 GitFlow 的保护，又失去了 GitHub Flow 的速度。**这是实践中最常见的失败形态。**

### 2.5 出问题了怎么办

**往前修，不往后退。** 合进去的坏代码，用一次"撤销提交"（revert）盖掉，再走一遍正常流程上线。

**不能**把 `main` 强行"回退"到昨天的状态——这会破坏所有人的本地副本，也销毁了事故记录。

如果坏功能是被开关包着的：**直接关开关，几秒解决，不用动代码。**

### 2.6 适合谁

| 适合 | 不适合 |
|---|---|
| 一周发布多次，或者合并了就上线 | 按月/按季度发版 |
| 团队小、沟通顺畅、代码审核认真 | 需要同时维护多个已发布版本 |
| Web 服务，部署完全由自己控制 | 发版需要合规签字、审计留痕 |
| 已经有（或愿意建）功能开关机制 | 做不到功能开关 |

> AWS 官方文档的原话：GitHub Flow "适合规模较小、成熟、沟通能力强的开发团队"，但"**如果你的团队有严格的合规或发布流程要求，它并不适合**"。

## 三、GitFlow

### 3.1 一句话本质

**有两条长期分支：`main` 代表"线上正在跑的版本"，`develop` 代表"下一版攒的功能"。发版前从 `develop` 切出一条 `release` 分支进入冻结期，只修 bug 不加新功能。**

### 3.2 长什么样

```
功能分支 ──▶ develop ──切──▶ release/1.4.0 ──▶ 打版本号 ──▶ 上线
                ▲                  │   （冻结期：只修 bug）      │
                │                  │                            ▼
                └──── 合并回来 ◀────┴──────────────────────▶ main
```

### 3.3 日常是什么节奏

1. 做功能 → 从 `develop` 拉分支 → 做完合回 `develop`
2. 到了发版节点 → 从 `develop` 切出 `release/1.4.0`，**进入冻结期**
3. 冻结期内：测试、只修 bug、不加新功能。同时 `develop` 继续接收下一版的功能
4. 测试通过 → 打上版本号（如 `v1.4.0`）→ 部署上线
5. **上线后必须把 release 分支合回 `main` 和 `develop` 两边**

### 3.4 关键点：两件必须做对的事

**第一，第 5 步的"合回两边"不能省。**

省掉它的后果：这一版修的 bug，下一版会原样复活。这是 GitFlow 最经典的事故。

**第二，线上紧急 bug（hotfix）必须从 `main` 拉分支，不能从 `develop` 拉。**

因为 `develop` 上有一堆还没测试过的新功能。从它拉分支去修线上问题，等于把没测过的东西一起推上线。

### 3.5 出问题了怎么办

线上紧急 bug：从 `main` 拉一条 hotfix 分支，修完走一遍压缩版的发版流程，上线后同样要合回 `main` 和 `develop`。

### 3.6 适合谁

| 适合 | 不适合 |
|---|---|
| 按计划发版（月度、季度、客户窗口期） | 一周发布多次 |
| 要同时维护多个版本（比如 2.3 还在服务老客户，3.0 已上线） | 团队小、追求快速迭代 |
| 发版需要合规签字、审计留痕 | 部署完全自己控制、没有版本概念 |
| 用户需要主动下载（App、私有化部署、SDK） | |
| 团队 git 经验较浅，或跨时区、审核较轻 | |

## 四、怎么选

### 4.1 真正的问题只有一个

不是"哪个更好"——两个都是成熟方案。真正的问题是：

> **没做完的工作放在哪里？放在分支里，还是放在功能开关后面？**

- 放分支里 → GitFlow。于是你需要 release 分支、冻结期、合并回两边这一整套。
- 放开关后 → GitHub Flow。于是你需要 `main` 永远可上线、审核门禁必须真的拦得住、分支必须短命。

**最糟的情况是两个都没回答**：分支活很久，又没有冻结期，也没有开关。这比任何一种规范做法都差。

### 4.2 决策表

按这三个维度问自己，**通常两三行就能定**：

| 如果这句话是真的 | 倾向 |
|---|---|
| 我们一周上线好几次 | **GitHub Flow** |
| 我们按月或按季度发版 | **GitFlow** |
| 我们要同时维护多个已发布版本 | **GitFlow** |
| 发版需要有人签字、需要审计记录 | **GitFlow** |
| 我们做不到"功能开关"，也不打算做 | **GitFlow** |
| 用户要主动下载我们的东西（App / 私有部署） | **GitFlow** |
| 团队小、审核认真、想持续快速上线 | **GitHub Flow** |
| 我们是网站/服务，部署完全自己说了算 | **GitHub Flow** |

**平手时的决胜局：问团队愿不愿意建功能开关机制。** 不愿意的团队不该选 GitHub Flow，无论发布多频繁。

### 4.3 两边的代价

| | GitFlow 的代价 | GitHub Flow 的代价 |
|---|---|---|
| 日常 | 维护 release 分支、每次发版都要合回两边 | 功能开关的纪律（尤其是用完要删）、频繁处理合并冲突 |
| 偷懒的后果 | 修好的 bug 复活、线上修复被覆盖 | 长命分支卷土重来，`main` 不再可靠 |
| 上手难度 | 高。分支类型多，规则多 | 入门低，但功能开关是真正的工程能力，不是约定 |

## 五、对 agent 怎么说（核心章节）

**你不需要记命令。你需要把意图说清楚，让 agent 自己选命令。**

下面每个场景给出：**该说什么**、**为什么这么说**、以及**不要说什么**。

### 5.1 刚接手一个项目，不知道用的什么工作流

> **说：** "先看一下这个仓库用的是哪种 Git 工作流——GitHub Flow 还是 GitFlow。把你看到的证据告诉我再下结论。如果证据不明确，别猜，直接问我。"

**为什么：** agent 很容易从仓库名字、技术栈或"上一个项目"想当然。要求它先给证据，你才能一眼看出它判断错没错。**"别猜，直接问我"这句要明确说出来**——否则它倾向于给一个自信的答案。

❌ 不要说："这个项目是 GitFlow 吧？" —— 这是在给它喂一个前提，它多半会顺着你说。

### 5.2 开始做一个新功能

> **说：** "我要做 [功能描述]。按这个仓库的工作流开一个分支，分支名符合仓库现有的命名习惯。"

如果预计要做很久，补一句：

> **补充：** "这个功能大概要做两周。按我们的工作流，应该拆成小块合并、用功能开关藏起来，还是开一个长期分支？给我建议和理由。"

**为什么：** 第二句是在防第二节讲的那个最常见失败——长命分支。让 agent 明确回答这个问题，比它默默开一个分支做两周要好。

### 5.3 准备上线

> **说：** "这个改动我要上线。按我们的工作流走完整流程，每一步做完告诉我当前状态。上线后要能说清楚线上跑的是哪个版本。"

**为什么：** 最后一句很重要。"线上跑的是哪个版本"这个问题，**在出事故的时候是最值钱的信息**，但平时没人记得要求。

❌ 不要说："直接部署到线上。" —— 跳过流程的指令，agent 有可能照做。

### 5.4 线上出了 bug，很急

> **说：** "线上出问题了：[现象]。先告诉我两件事：能不能用关功能开关解决？如果不能，是撤销之前那个改动快，还是往前修一个补丁快？**先别动手，等我确认。**"

**为什么：** 这是**最危险的场景**，因为"急"会让人和 agent 都跳过检查。

- 先问"能不能关开关"是因为它最快、最安全、不用改代码
- "先别动手，等我确认"是刹车。紧急情况下 agent 可能做出不可逆的操作

❌ **绝对不要说：** "把 main 回退到昨天的状态" / "强推一个修复上去"。这类操作会破坏所有人的本地副本，还会销毁事故记录。**正确的做法永远是"往前修"，不是"往后退"。**

### 5.5 我不知道该怎么办

> **说：** "我现在的情况是 [描述]。按我们的工作流，正确做法是什么？给我两三个选项和各自的风险，我来选。"

**为什么：** 让 agent 给选项而不是直接执行，是非技术人员最有用的一个习惯。你不需要懂命令，但你能判断"哪个风险我能接受"。

### 5.6 新项目，还没定工作流

> **说：** "新项目要定 Git 工作流。先问我几个问题——发布频率、要不要维护老版本、有没有合规要求——再给建议。"

**为什么：** 直接问"用哪个好"，得到的多半是泛泛而谈。让它先问你，答案才贴合你的实际情况。

### 5.7 一句万能兜底

任何时候都可以说：

> **"你打算执行什么操作？这个操作可逆吗？先说，别做。"**

**"可逆吗"是非技术人员能问出的最有价值的技术问题。** 不可逆操作出错的代价，和可逆操作完全不是一个量级。

## 六、三条危险信号

看到这些，停下来问清楚。

### 🔴 信号一：有人要"直接推到 main"

**听起来像：** "改动很小，走流程太麻烦了。" "就改一个字。"

**为什么危险：** 绕过了所有检查。而且"就这一次"会变成惯例——真正需要保护的那天，门禁早就形同虚设了。

**你该说：** "还是走 PR 吧，小改动走流程也很快。如果是流程太慢，我们单独讨论怎么让它快一点。"

### 🔴 信号二：某个分支已经活了好几周

**听起来像：** "这个功能比较大，等做完了再合。"

**为什么危险：** 这条分支实际上已经变成了一个没有任何保护规则的 release 分支。合并它的时候会是一场硬仗，而且冲突越积越多。

**你该说：** "能不能拆成几块分批合进去，没做完的部分用功能开关关着？如果实在拆不开，说明我们可能需要换工作流，值得单独讨论。"

### 🔴 信号三：出事时有人提"强推"或"回退 main"

**听起来像：** "force push 一下就好了。" "把 main reset 到昨天。"

**为什么危险：** 这是本手册里**唯一一条真正不可逆**的操作。它会破坏每个人的本地副本，销毁"到底发生了什么"的证据——而事后复盘恰恰需要这些证据。

**你该说：** "不要强推。用 revert 撤销那个改动，再走正常流程上线。"

## 七、术语表

| 术语 | 中文 | 一句话解释 |
|---|---|---|
| branch | 分支 | 项目的一份平行副本，改它不影响别人 |
| `main` / `master` | 主干 | 代表正式版本的那条分支，受保护 |
| `develop` | 开发分支 | GitFlow 里攒下一版功能的地方 |
| `release` branch | 发布分支 | GitFlow 的冻结期分支，只修 bug 不加功能 |
| hotfix | 紧急修复 | 修线上问题的分支，GitFlow 里必须从 `main` 拉 |
| PR / MR | 合并请求 | 把分支合进主干前的审核环节 |
| merge | 合并 | 把分支的改动并入另一条分支 |
| squash | 压缩合并 | 把分支上的多个提交压成一个再合并 |
| revert | 撤销提交 | 用一个新提交抵消之前的改动。**安全、可追溯** |
| force push / reset | 强推 / 回退 | 改写历史。**不可逆，正常流程中不该出现** |
| tag | 版本标签 | 给某个时间点的代码打一个不可变的名字，如 `v1.4.0` |
| feature flag | 功能开关 | 能在线上随时开关某功能的配置，不用改代码 |
| back-merge | 合并回来 | GitFlow 里上线后把 release 合回 `main` 和 `develop` |
| CI | 持续集成 | 自动跑测试和构建的机器人 |
| branch protection | 分支保护 | 锁住 `main`，禁止直接推送 |

## 八、一页速查

**通用底线（两种工作流都适用）：**

1. 任何改动都要经过 PR，不直接推 `main`
2. 要能随时说清楚"线上跑的是哪个版本"
3. 出问题往前修（revert），不往后退（force push）

**GitHub Flow：** 一条 `main` 永远可上线 · 分支活 1~2 天 · 没做完的用功能开关藏 · 出事 revert 后前滚

**GitFlow：** `main` + `develop` 两条长期分支 · 发版切 release 分支进冻结期 · 上线后必须合回两边 · hotfix 从 `main` 拉

**对 agent 的万能兜底：** "你打算执行什么操作？这个操作可逆吗？先说，别做。"
